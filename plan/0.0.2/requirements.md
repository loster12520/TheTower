## 1. 背景与问题定义

0.0.1 已完成基础闭环，但工程质量存在明显短板：
- 代码风格与命名不统一，阅读成本高；
- 注释粒度不稳定，知识无法沉淀；
- 前端内联样式较多，组件职责不够清晰；
- 后端仍以内存为主，缺少持久化与迁移策略；
- 统一日志、错误码、缓存策略等基建不完整。

本版本不追求新增复杂业务节点，而是优先修复“可维护性与可扩展性”基础问题。

---

## 2. 版本边界与阶段目标

### 2.1 本版必须完成
1. 建立项目级规范体系（注释、命名、复杂度、文件长度、重构安全网）。
2. 前后端核心基建补齐（配置中心、请求层、WS 层、统一响应、日志、缓存、持久化）。
3. 形成流程化交付资产（plan/requirements/steps/tech/test/result + backend-test.py）。

### 2.2 本版不做
1. 不扩展新的业务节点类型（if/loop 等控制流继续延后）。
2. 不做多租户、权限系统、调度系统。
3. 不做大规模 UI 视觉重设计（仅做结构规范化与样式抽离）。

## 3. 代码规范化需求

### 3.1 注释体系升级

- 前端：组件、状态、函数、副作用代码块必须具备注释，注释说明“意图 + 输入输出 + 边界行为”。
- 后端：类、属性、方法必须具备 KDoc；复杂逻辑段必须有块级说明。
- 当自定义函数超过可读阈值（建议 >10 行且存在多段逻辑）时，必须按功能拆分，并在分块前给出功能注释。

### 3.2 注释白名单/黑名单方案（本版必交付）

> 本节定义“需求稿必须给出的具体限制方案”，用于避免过度注释或注释缺失。

#### 3.2.1 白名单（必须高密度注释）
- `frontend/src/pages/**`
- `frontend/src/stores/**`
- `frontend/src/services/**`
- `backend/src/main/kotlin/com/thetower/routes/**`
- `backend/src/main/kotlin/com/thetower/services/**`
- `backend/src/main/kotlin/com/thetower/repository/**`

规则：
- 文件头必须有职责说明；
- 每个对外方法必须有注释；
- 复杂分支/副作用代码块必须有块注释。

#### 3.2.2 灰名单（允许简化注释）
- `frontend/src/models/**`
- `backend/src/main/kotlin/com/thetower/models/**`
- `frontend/src/utils/**`
- `backend/src/main/kotlin/com/thetower/utils/**`

规则：
- 类型定义与纯函数可使用简要注释；
- 重复性字段无需逐行解释，但关键字段必须解释语义。

#### 3.2.3 黑名单（禁止注释膨胀）
- 构建产物、第三方代码、自动生成文件（如 `build/**`、`node_modules/**`、生成的 SDK 文件）。

规则：
- 不做逐行注释；
- 仅在必要时保留“来源说明/禁止手改说明”。

#### 3.2.4 验收口径
- 白名单文件注释合规率需达到 95%+；
- 黑名单文件不得出现大规模人工注释提交；
- 抽查时每个模块至少 3 个文件符合规则。

### 3.3 复杂度与文件长度阈值

- 函数复杂度阈值：默认 `Cyclomatic Complexity <= 10`（超限必须拆分并附说明）。
- 文件长度阈值：默认 `<= 400` 行（超限需拆分模块并标注拆分方案）。
- 单函数长度阈值：建议 `<= 60` 行（超过须说明不可拆分原因或强制拆分）。
- 必须接入自动化检查（lint/静态规则），不能仅靠人工评审。

### 3.4 命名词典规则

- 动词用于行为：`get/create/update/delete/start/cancel/restart/validate/parse/emit`。
- 名词用于状态与实体：`template/run/status/event/payload/response/context/repository`。
- 前后端术语统一中英映射，至少包含：
  - 模板 = template
  - 运行 = run
  - 步骤 = step
  - 事件 = event
  - 错误码 = errorCode
  - 缓存 = cache
- routes 与 services 同语义命名：例如 `getTemplates` 在两层保持一致。

### 3.5 重构安全网

重构类改动必须通过以下门禁：
1. 编译通过（frontend build / backend build）。
2. 静态检查通过（lint、复杂度、长度规则）。
3. 核心测试通过（后端接口自动化 + 关键前端页面链路）。
4. 回归清单通过（模板创建、保存、运行、取消、删除）。
5. 变更说明完整（重命名映射、迁移影响、回滚方案）。

### 3.6 目录与样式规范化

- 前端页面域收敛：页面与其相关状态/组件按域组织，减少横向散落。
- 前端样式抽离：页面与组件样式统一迁移到 `.scss` 文件，禁止新增大段内联样式。
- `src` 下 import 统一使用 `@` 别名。

## 4. 前后端基建需求

### 4.1 前端运行时配置中心

必须支持以下配置项在运行时注入：
- API Base URL
- WebSocket Base URL
- 鉴权开关与 token header 策略
- 日志开关与级别

要求：
- 开发/测试/生产环境可切换；
- 禁止把环境地址硬编码在业务组件中。

### 4.2 前端请求层规范化

- 统一请求入口（拦截器 + 错误处理 + 响应规范化）。
- 开发环境输出请求日志与响应摘要。
- 自动注入 token/Header。
- 统一错误兜底与用户提示策略。

### 4.3 前端 WebSocket 规范化

- 提供按字符串 key 获取单例连接的工厂函数。
- 自动重连策略（指数退避，最大重试次数可配置）。
- 心跳保活（ping/pong 或约定心跳包）。
- 消息加密/解密封装（最小可用实现，后续可替换更强方案）。

### 4.4 后端统一响应与错误码体系

- 统一返回体结构，提供便捷成功返回调用（`data.success()` 风格）。
- 统一错误码格式，禁止重复定义或语义冲突。
- 错误码与 HTTP 状态映射必须一致且文档化。

### 4.5 后端日志分级与链路标识

- 统一日志级别：`debug/info/warn/error`。
- 接口请求必须带 `requestId`（或等价链路 id）并全程透传。
- 错误日志必须包含错误码与上下文最小字段。

### 4.6 后端缓存与失效策略

- 先实现内存缓存用于高频读接口。
- 必须包含失效策略：
  - TTL 自动过期；
  - 写操作触发主动失效；
  - 可选手动清理入口。
- 缓存命中/失效需可观测（至少日志可追踪）。

### 4.7 后端 SQLite + Jimmer 持久化

- 模板、运行等核心数据从内存迁移到 SQLite。
- 使用 Jimmer 构建实体映射与数据访问。
- 保证原有 API 语义不变，避免前端联调破坏。

### 4.8 数据库迁移机制（次高优先级）

- 建立 schema 版本管理与迁移脚本机制。
- 支持从空库初始化与版本升级。
- 该项优先级低于核心链路可用性，但必须在 0.0.2 完成最小可用方案。

## 5. 错误码登记表需求

必须新增错误码登记表文档（建议置于 `plan/0.0.2/steps/api.md` 或独立 `error-codes.md`），至少包含：
- 错误码
- 语义描述
- HTTP 状态码
- 触发场景
- 前端提示建议
- 处理建议（可重试/不可重试）

要求：
- 新增错误码必须先登记后使用；
- 禁止“一码多义”与“同义多码”。

## 6. 版本流程要求（强制执行）

本版严格按以下顺序推进：
1. 版本目标（`plan/${version-code}/plan.md`）
2. 需求稿（`plan/${version-code}/requirements.md`）
3. 版块实施文档（`plan/${version-code}/steps/{api.md,backend-plan.md,frontend-plan.md}`）
4. 技术实现报告（`report/${version-code}/tech.md`）
5. 测试文档模板（`report/${version-code}/test.md`，先不填结果）
6. 后端开发
7. 后端接口自动化测试（`test/${version-code}/backend-test.py`）
8. 前端开发
9. 前端测试（按测试计划执行）
10. 黑盒功能测试（按测试计划执行）
11. 缺陷修复
12. 版本结果汇总（`report/${version-code}/result.md`）

约束：若后续阶段需改动前置文档，必须先与用户确认。

## 7. 验收标准（必须量化）

### 7.1 规范与重构验收
- 白名单注释合规率 >= 95%。
- 函数复杂度超阈值项清零或附批准豁免记录。
- 文件长度超阈值项清零或附拆分计划与截止日期。
- 命名词典抽样一致率 >= 95%。

### 7.2 基建能力验收
- 前端运行时配置可切换环境并生效。
- 请求层、WebSocket 层统一入口生效，旧散落入口逐步收敛。
- 后端统一响应体与错误码机制可用。
- 日志分级、requestId 透传可观测。
- 缓存 TTL 与主动失效可验证。
- SQLite + Jimmer 持久化跑通核心 CRUD。
- 数据库迁移从 V1 到 V2 可执行。

### 7.3 流程交付验收
- `plan/report/test` 资产齐全且结构正确。
- 后端自动化脚本可一键执行并输出结果。
- `result.md` 对需求完成度、问题与剩余风险有明确结论。

---

## 8. 非目标与风险说明

### 8.1 非目标
- 本版不追求业务功能大扩展；
- 不做多租户、权限、调度等复杂系统。

### 8.2 主要风险
- 大规模重构引入回归风险；
- 基建一次性升级导致工期压力；
- Jimmer + SQLite 迁移期间可能出现兼容问题。

应对策略：
- 分阶段提交，保证每个阶段可编译、可测试、可回滚；
- 先核心路径后扩展路径，避免并行改动过多。

总结：0.0.2 的价值在于把“规范、基建、流程、验收”建立为可执行体系，为后续功能迭代提供稳定工程基础。
