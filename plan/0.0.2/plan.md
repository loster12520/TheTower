# 0.0.2 版本目标（基建与流程完善）

导语：本版本聚焦“规范化与可持续开发”，通过 AI 协作约束、代码规范重构、前后端基建升级与流程固化，为后续功能迭代建立稳定底座。

## 1. AI 协作规范与项目级 Skill 建设

1.1 建立项目级新 Skill，统一定义代码风格、注释标准、命名规则、目录职责与开发流程约束。  
1.2 在 Skill 中明确“先文档后开发”的顺序要求，约束每个版本必须完成计划、需求、技术设计、测试设计。  
1.3 在 Skill 中加入“变更边界控制”规则：后续阶段若需改动前置产物，先与用户确认再修改。  
1.4 在 Skill 中补充“文件路径职责地图”，明确 `pages/components/stores/services/routes/services/repository/models` 的职责。

## 2. 现有代码规范化重构

2.1 完成前后端注释规范升级：为每个类、属性、方法、关键变量、关键副作用代码块补充完整注释（接近 JavaDoc/KDoc 风格）。  
2.2 在需求稿阶段产出“注释范围白名单/黑名单方案”：明确必须全量注释的目录、可简化注释的目录、无需逐行注释的生成文件目录，并给出执行与验收规则。  
2.3 前端样式从 TSX 内联样式中抽离，统一迁移到 SCSS 文件，组件中只保留结构与状态逻辑。  
2.4 统一命名规范（文件名、函数名、变量名），减少语义不一致与缩写混乱。  
2.5 前端目录按“页面域”收敛：同一页面相关资源放入同名子目录（如 `pages/edit/*`、`stores/edit/*`）。  
2.6 后端 routes 与 services 采用 API 语义化命名并一一对应（例如 `getTemplates`、`createTemplate`、`restartRun`）。  
2.7 增加“最大函数复杂度阈值”与“最大文件长度阈值”规则，并在 lint/CI 中做自动检查。  
2.8 建立命名词典规则：动词用于函数、名词用于状态，统一中英文术语表并纳入评审清单。  
2.9 增加“重构安全网”要求：重构后必须通过编译、静态检查、核心测试与关键路径回归。

## 3. 前后端基建升级

3.1 前端主题体系：提供全局 theme 切换能力（至少明暗双主题），并保证组件级样式可继承。  
3.2 前端路径与导入规范：`src` 下 import 全部使用 `@` 前缀别名，消除相对路径层级噪音。  
3.3 前端请求层规范化：开发环境请求日志、统一错误兜底、自动注入 token/Header、按环境自动切换服务器地址。  
3.4 增加前端运行时配置中心：支持按环境动态注入 API 地址、WS 地址、开关配置与鉴权策略。  
3.5 前端 WebSocket 规范化：单例工厂（按 string key 获取）、自动重连、心跳保活、消息加密/解密封装。  
3.6 后端统一返回体升级：全局唯一错误码体系、响应便捷调用（如 `data.success()` 风格）。  
3.7 后端统一日志分级：按 `debug/info/warn/error` 输出，支持请求链路追踪字段。  
3.8 后端高频接口缓存：先以内存缓存实现部分读多写少接口的结果复用，并增加 TTL 与主动失效策略。  
3.9 后端数据持久化：存储从内存实现切换到 SQLite，并采用 Jimmer 进行 ORM/数据访问层建设。  
3.10 后端数据库迁移机制：建立版本化迁移流程（优先级次高于核心链路，但纳入本版本交付）。  
3.11 建立统一错误码登记表：文档化错误码、语义、HTTP 映射与使用边界。

## 4. 版本开发流程固化（执行清单）

4.1 先产出版本目标文档：`plan/${version-code}/plan.md`。  
4.2 再产出需求稿：`plan/${version-code}/requirements.md`（必须包含“注释白名单/黑名单方案”“复杂度与文件长度阈值方案”“命名词典方案”）。  
4.3 再拆分版块实施文档：`plan/${version-code}/steps/{api.md,backend-plan.md,frontend-plan.md}`。  
4.4 产出技术实现报告：`report/${version-code}/tech.md`（含实现路径、关键代码、预期改动文件）。  
4.5 产出测试文档模板：`report/${version-code}/test.md`（先给完整表格，不预填结果）。  
4.6 执行后端开发。  
4.7 执行后端接口自动化测试：`test/${version-code}/backend-test.py`。  
4.8 执行前端开发。  
4.9 执行前端测试（按测试计划逐步验证）。  
4.10 执行黑盒功能测试（按测试计划逐步验证）。  
4.11 集中修复缺陷。  
4.12 输出版本总结：`report/${version-code}/result.md`。

## 5. 版本完成判定（0.0.2）

5.1 规范落地可检查：注释覆盖率、注释白名单/黑名单执行率、命名词典一致性、样式抽离率、import 别名使用率可验证。  
5.2 工程质量可检查：函数复杂度阈值、文件长度阈值、重构安全网检查项均可自动化验证。  
5.3 基建能力可验证：主题切换、运行时配置中心、请求统一层、WebSocket 统一层、后端统一返回体、日志分级、缓存失效策略、SQLite 持久化、数据库迁移机制均可运行。  
5.4 流程资产齐全：`plan/report/test` 对应文档、错误码登记表与测试脚本按目录约定完整交付。

总结：0.0.2 的核心不是新增业务功能，而是把“开发规范、代码质量、工程基建、流程执行”四个基础面一次补齐。
