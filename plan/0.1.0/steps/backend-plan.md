# 0.1.0 后端实施文档（执行引擎扩展 + 调试状态机升级 + 平台能力落地）

导语：本文档用于拆分 0.1.0 后端主线，目标是在不破坏现有模板与运行主链路的前提下，把体验增强、高级调试、外部集成和产品化能力逐步落到稳定实现上。

## 1. 实施目标与边界

- 目标：把 0.1.0 的新增能力拆成可独立推进的后端模块。
- 目标：保证所有新增节点和平台能力进入统一校验、执行、错误码和持久化体系。
- 目标：先稳定协议和状态机，再进入跨模块实现，降低返工。
- 边界：本文件不直接替代详细设计，只给出主线、依赖关系和验收顺序。

## 2. 后端主线

| 模块 | 0.1.0 关注点 |
|---|---|
| TemplateService / Repository | 搜索、标签/分组、克隆、批量删除、自动保存支撑 |
| RunService | 统一运行参数、调试扩展、调度触发入口 |
| DebugService | 条件断点、时间旅行、远程操控状态机 |
| Step Registry / Executor | 数据文件节点与请求监听节点注册与执行 |
| Auth / Tenant / Collaboration | 用户、权限、租户、协作的最小闭环 |
| Scheduler | 定时执行、失败重试、任务状态追踪 |

## 3. 分模块实施建议

### 3.1 模板与体验增强支撑

- 模板持久化模型增加标签、分组、更新时间和自动保存辅助字段。
- 首页查询支持关键字、标签、分组过滤与分页组合。
- 克隆能力需深拷贝步骤、画布结构与元信息，并生成新 ID 与时间戳。
- 批量删除需返回成功数、失败数和失败原因列表。

### 3.2 运行参数统一

- `StartRunRequest` 与调试启动入口统一复用运行参数对象。
- 运行参数至少覆盖浏览器类型、headless、默认超时和启动变量。
- 参数入库或写入运行快照，便于调试复现和时间旅行回看。

### 3.3 高级调试状态机

- 在现有暂停、继续、单步状态上补条件断点命中原因。
- 增加历史帧、变量快照和页面上下文快照的落盘或内存保留策略。
- 远程操控动作必须绑定到当前调试会话，且动作结果需事件化回传。
- 需要定义内存保留上限，避免时间旅行调试拖垮长流程执行。

### 3.4 节点能力扩展

- 为 `saveData`、`saveExcel`、`importExcel`、`getClipboardText`、`extractActiveElement` 定义统一配置校验器。
- 为 `listenRequestTrigger`、`listenRequestResult`、`stopPageListen` 建立监听生命周期管理，避免 run 结束后残留监听器。

### 3.5 平台能力落地

- 调度任务需与模板、运行记录和租户空间关联。
- 模板市场至少要支持模板发布、导入、版本信息和来源追踪。
- 用户与权限需先完成最小角色模型，再接入模板、运行和协作资源。
- 协作编辑优先实现会话存在感知、基础冲突提示和变更广播。

## 4. 数据与存储约束

- 若继续使用 SQLite，需要评估调度、协作和多用户并发写入的可接受范围。
- 时间旅行调试的快照建议区分“内存缓存”和“磁盘产物”，避免全部常驻内存。
- 第三方凭证不应写入模板明文，至少要有配置隔离或引用式存储方案。

## 5. 测试重点

1. 搜索、克隆、批量删除和自动保存不会破坏现有模板 CRUD 主链路。
2. 运行参数在普通运行和调试运行下行为一致。
3. 条件断点、时间旅行和远程操控在长链路场景下仍能收敛到稳定状态。
4. 新增节点在成功、失败、重试和外部依赖波动下都能给出稳定业务码。
5. 调度、权限和协作能力不会污染单机单用户的既有运行路径。

## 6. 交付物

- 后端实现变更与数据库结构调整。
- `test/0.1.0/backend-test.py` 与新增专项脚本。
- `report/0.1.0/tech.md` 中的后端实现记录。
- `docs/api-reference.md` 与 `docs/deployment.md` 的后端补充章节。

## 7. 实施顺序

1. 先完成模板体验增强与运行参数统一。
2. 再完成高级调试状态机与事件扩展。
3. 再完成数据文件节点与外部平台适配层。
4. 最后完成调度、权限、市场与协作主线。

总结：0.1.0 后端的关键不是把模块越做越多，而是让新增能力都进入同一条可维护、可测试、可追踪的主干链路。
