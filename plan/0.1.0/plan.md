## 1. 版本定位

- 0.0.9 已完成工程化补完、本地指标验收、交付文档整理与部署手册沉淀。
- 0.1.0 的任务不再是补“某一个缺口”，而是一次性承接当前未完成清单中的所有条目。
- 本版完成后，TheTower 应从“可答辩、可本地交付”进入“功能更完整、使用更顺手、可扩展性更强”的产品化初期阶段。

## 2. 版本目标

| 目标项 | 优先级 | 说明 | 验收信号 |
|---|---:|---|---|
| 云部署实机验收闭环 | P0 | 把 0.0.9 已准备的部署手册、部署样例与验收模板落到真实云环境 | 完成真实云机部署并回填验收记录 |
| 编辑器体验补完 | P0 | 一次性补齐自动保存、搜索、标签分组、克隆、自动布局、批量删除等高频体验能力 | 用户在模板管理与编辑页的高频重复操作显著减少 |
| 运行参数面板完善 | P0 | 把浏览器类型、超时、headless 等关键运行参数做成明确的可视化入口 | 运行前参数可在 UI 中完整配置并持久化 |
| 高级调试首版 | P0 | 补齐条件断点、时间旅行调试、预览远程操控三类增强调试能力 | 调试工作台可覆盖复杂排障场景 |
| 数据与文件集成 | P1 | 补齐本地文件、Excel、剪贴板、焦点元素等通用数据节点 | 典型数据输入输出场景可直接编排 |
| 网络与第三方平台接入 | P1 | 补齐请求监听、Google Sheet、邮箱、验证码平台与 LLM 集成入口 | 外部平台协同场景可形成最小闭环 |
| 产品化能力首版 | P1 | 启动计划任务、模板市场、多用户权限与协作编辑等平台能力 | 系统开始具备“单机工具”之外的产品形态 |

## 3. 纳入来源

- 来源一：`report/unimplemented-features.md` 中全部未完成条目统一并入 0.1.0。
- 来源二：0.0.9 版本结论已明确，本地交付版本成立，但真实云环境交付、体验增强和产品化能力尚未闭环。
- 来源三：用户当前明确要求“这些全部放到 0.1.0 中实现，并从需求稿开始冻结范围”。

## 4. 本版范围

### 4.1 交付闭环补完

- 完成真实云服务器部署验收。
- 把云部署结果回填到测试报告与版本总结。
- 固化部署目录、systemd、Nginx、环境变量与浏览器依赖方案。

### 4.2 编辑器体验增强

- 自动保存。
- 模板搜索。
- 模板标签或分组。
- 模板复制或克隆。
- 节点自动布局。
- 模板批量删除。
- 运行参数面板增强。

### 4.3 高级调试增强

- 条件断点。
- 时间旅行调试。
- 调试预览远程操控。

### 4.4 数据与外部集成

- `saveData`、`saveExcel`、`importExcel`、`getClipboardText`、`extractActiveElement`。
- `listenRequestTrigger`、`listenRequestResult`、`stopPageListen`。
- `googleSheet`、`getEmail`、2Captcha 或同类打码平台、OpenAI 或 LLM 集成。

### 4.5 产品化能力首版

- 计划任务或定时执行。
- 模板市场。
- 多用户、权限隔离、多租户基础。
- 协作编辑。

### Phase C：高级调试主线

- 完成协作编辑首版

## 6. 主要风险

| 风险 | 影响 | 缓解策略 |
|---|---|---|
| 范围一次性过大 | 版本周期显著拉长 | 用 Phase 切分并在需求文档中明确子模块验收 |
| 高级调试实现复杂 | 前后端联动成本高 | 先冻结调试状态机与协议，再分层实现 |
| 外部平台依赖不稳定 | 第三方接入测试波动大 | 所有第三方能力都保留降级策略与 mock 方案 |
| 产品化能力跨层改动大 | 影响既有模板与运行主链路 | 先隔离认证、任务调度和协作模型，再逐步接入主流程 |
| 云部署环境差异 | 验收结果不稳定 | 统一部署样例文件和验收模板，记录真实运行环境 |

## 8. 版本完成判定

1. `report/unimplemented-features.md` 当前列出的全部条目均已在 0.1.0 完成或被吸收进实现闭环。
2. 云部署实机验收已完成并有可追溯记录。
3. 编辑器体验增强项已全部上线并通过回归。
4. 高级调试三项能力均可真实使用。
5. 数据与外部集成节点已形成可编排、可执行、可测试的最小闭环。
6. 产品化能力首版已形成真实入口，而不是仅有文档规划。

总结：0.1.0 的核心目标是把 TheTower 当前所有剩余能力一次性纳入正式版本范围，并通过完整需求与实施文档把“未完成清单”清零。
