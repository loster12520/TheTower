## 范围与非目标

- 范围：围绕毕业设计原始技术指标补齐专项验证，至少覆盖画布性能、浏览器兼容、并发执行和成功率说明。
- 范围：统一仓库当前版本口径，修复 README、汇总文档与真实实现不一致的问题。
- 范围：补齐用户操作文档、API 文档、部署文档与关键运行说明。
- 范围：纠正浏览器支持与配置口径，明确 Chrome、Firefox、Edge 的真实支持方式。
- 范围：在主线工作完成后，评估自动保存、模板搜索、模板克隆、自动布局等效率增强项。
- 非目标：不在本版大规模新增步骤家族。
- 非目标：不在本版扩展协作、多租户、模板市场与外部平台集成。
- 非目标：不在本版推进条件断点、时间旅行调试或远程预览操控。

## 0.0.9 技术指标验收

### 1. 画布性能验证

- 需要新增“50 节点画布”专项场景，覆盖初始渲染、拖拽、缩放、选中、保存等关键交互。
- 需要定义响应时间统计口径，至少明确是交互响应、渲染稳定还是保存时延。
- 测试结果应输出为可记录的时间数据，而不是只写“体感流畅”。
- 若无法稳定达到 200ms，应给出瓶颈定位、当前实测区间和改进计划。

### 2. 浏览器兼容性验证

- 需要明确区分“代码支持口径”和“真实验收口径”。
- Chrome、Firefox、Edge 三浏览器至少应在同一组或等价场景下完成一次真实运行验证。
- 若 Edge 实际使用 Playwright 的 channel 模式或系统 Edge，可按真实实现说明；若当前不满足，应先修正实现或下调文案口径。
- 调试模式与普通运行模式在不同浏览器上的差异需明确记录，避免答辩时被追问。

### 3. 并发执行验证

- 需要构造至少 3 个流程同时运行的测试场景。
- 验证点至少包括：都能启动、状态互不污染、事件流可区分、完成结果可回收。
- 若数据库或浏览器资源限制导致偶发不稳定，需要记录边界条件与建议配置。

### 4. 成功率与稳定性验证

- 需要明确“成功率 ≥ 95%”的统计方式，例如重复运行 20 次、50 次或按模板样本池统计。
- 需要定义成功、失败、取消的统计口径。
- 需要至少输出一组能进入论文的统计结果，而不是只保留零散回归通过记录。

## 0.0.9 文档与仓库口径收口

### 1. README 与项目概览更新

- 根 README 需要同步到当前版本阶段，不再停留在 0.0.4 叙述。
- 项目概述、架构图、节点清单、测试结果、当前范围都要更新到 0.0.8 已实现状态。
- README 应能够承担“仓库首页答辩展示入口”的作用。

### 2. 已实现与未实现清单修正

- `report/implemented-feature-summary.md` 需要同步默认版本、节点数量、运行能力与测试口径。
- `report/unimplemented-features.md` 需要移除已经在 0.0.8 完成的项目，如 `keyboardPress`、`keyboardHotkey`、`textExtract`、`goBack`、`closeOtherPages` 与元素引用增强。
- 已完成项和未完成项之间不能再互相矛盾。

### 3. 用户操作文档

- 需要整理一份面向普通使用者的操作文档。
- 至少覆盖：环境准备、启动前后端、创建模板、拖拽编排、配置节点、保存模板、普通运行、调试运行、查看日志与产物、失败定位。
- 文档语言应尽量偏用户视角，而不是只写内部实现名词。

### 4. API 文档与错误码文档

- 需要覆盖模板接口、运行接口、调试接口、WebSocket 事件与关键错误码。
- 文档应同时给出请求示例、响应示例和字段说明。
- 若协议在 0.0.8 有新增状态，如调试保留态和步骤名称字段，也需要明确记录。

## 0.0.9 部署与运行规范

### 1. 本地部署规范

- 需要明确前后端启动顺序、默认端口、依赖要求、数据库路径和浏览器依赖。
- 需要记录常见问题，如端口冲突、Playwright 浏览器安装、Gradle Wrapper 缺失、Windows 环境差异。
- 需要形成一条稳定、可复制的本地运行路径。

### 2. 环境变量与配置规范

- 需要明确 `PORT`、WebSocket 基地址、是否 mock、数据库路径、浏览器类型等关键配置项。
- 配置说明必须与代码行为一致，避免“文档写一个，入口实际读另一个”的情况。
- 应补充调试模式与生产模式下的重要配置差异。

### 3. 云部署或容器化准备

- 若时间允许，建议补齐 Dockerfile、基础部署说明或最小云服务器部署路径。
- 若本版不落地完整云部署，也至少需要写清推荐部署架构和后续接入方式。
- 目标不是上云本身，而是满足“系统支持部署在本地或云服务器”的论证要求。

## 0.0.9 产品与工程增强

### 1. 运行参数面板完善

- 现有运行能力已支持部分浏览器和调试参数，但用户侧配置入口仍偏弱。
- 建议补充浏览器类型、headless、超时等参数的可视化配置能力。
- 如果无法一次做完整，也可以先做最小可配置集。

### 2. 编排效率增强

- 自动保存：减少因忘记保存导致的上下文丢失。
- 模板搜索：降低模板数量增多后的查找成本。
- 模板克隆：降低从相似模板重复起步的成本。
- 自动布局或节点对齐：提高大画布的整理效率。

### 3. 运行质量统计展示

- 建议为运行列表或详情页增加耗时、成功率、失败原因摘要等信息。
- 这些信息既能增强产品感，也能直接服务论文里的测试分析章节。

## 前后端实现约束

### 前端约束

- 文档更新必须与真实 UI 行为保持一致，不再用过期截图或旧版本术语。
- 性能测试应优先复用现有 Playwright 或前端测试基础设施，避免引入难维护的独立脚本体系。
- 效率增强能力只做最小闭环，不为追求“看起来很多功能”而稀释主线。

### 后端约束

- 浏览器支持实现必须与文档口径一致，尤其是 Edge 支持方式需要明确。
- 并发能力验证应在现有协程与运行状态模型上完成，不新增一套专用执行框架。
- 部署说明中的端口、数据库路径、环境变量与入口读取逻辑必须一致。

### 协议约束

- API 文档、错误码文档与当前实现统一维护，避免 README 与报告各写各的。
- WebSocket 事件说明必须覆盖当前已存在的运行与调试扩展事件。

## 测试与验收口径

1. 画布性能验收
   - 构造 50 节点场景并执行关键交互。
   - 验收点：能输出响应时间与稳定性结果，并对照目标说明是否达标。

2. 浏览器兼容验收
   - 在 Chrome、Firefox、Edge 三浏览器下执行同类流程。
   - 验收点：核心流程可运行，失败差异可说明，文档口径与实现一致。

3. 并发执行验收
   - 同时发起至少 3 个流程运行。
   - 验收点：状态隔离正常、运行结果可回收、无明显互相污染。

4. 文档交付验收
   - 按用户文档从零启动并完成一次模板编排与运行。
   - 验收点：不依赖口头补充也能完成主流程。

5. API 文档验收
   - 按文档调用主要接口和订阅事件。
   - 验收点：文档内容与实际响应一致。

6. 部署文档验收
   - 在干净环境按部署文档启动系统。
   - 验收点：能够完成最小部署并访问健康检查及前端页面。

7. 效率增强验收
   - 对自动保存、搜索、克隆、自动布局中实际纳入的能力逐项验证。
   - 验收点：能力可感知、不会引入主链路回归。

## 延期项

| 类别 | 延期项 | 延期原因 |
|---|---|---|
| 外部集成 | Excel、Google Sheet、邮件、网络监听等 | 不是答辩前最短补齐路径 |
| 高级调试 | 条件断点、时间旅行调试、远程操控预览 | 对版本主目标贡献有限，成本高 |
| 平台化能力 | 模板市场、多人协作、多租户、登录体系 | 超出当前毕设收口范围 |
| 大规模新节点扩展 | 更多长尾操作节点 | 当前优先级低于指标与文档交付 |

总结：0.0.9 的交付标准不是“再加很多新功能”，而是把已有系统补到“指标可说明、文档可复现、部署可落地、版本可自洽”的工程完成度，为毕业论文、答辩演示和后续继续开发提供稳固基线。
