# 0.0.3 详细需求（模板导入/导出 + 运行可观测性）

导语：本文档把 0.0.3 的目标拆成可实现、可测试、可验收的条款，避免“做了但不可验证”。

## 1. 模板导入（P0）

### 1.1 入口
- 页面：首页。
- 交互：点击“导入模板”按钮后选择 `.json` 文件。

### 1.2 支持的文件格式
- 支持导入由 TheTower 导出产生的 JSON 文件。
- schemaVersion 必须为 `0.0.1`（当前画布与后端编译器仍为线性流程）。

### 1.3 导入行为
- <u>解析</u> JSON 并进行最小校验：`name/schemaVersion/steps/otherStep`。
- <u>创建</u> 新模板（name/description），并 <u>保存</u> steps/otherStep。
- 导入成功后刷新列表；导入失败给出明确错误提示。

### 1.4 验收
- 导入后模板可进入编辑页正常渲染。
- 导入后能运行并收到 WS 事件。

## 2. 模板导出（P0）

### 2.1 入口
- 页面：首页模板卡片右侧“更多”下拉菜单。
- 交互：点击“导出”后下载 `.json` 文件。

### 2.2 导出行为
- <u>获取</u> 模板详情（包含 steps/otherStep）。
- <u>下载</u> JSON 文件，文件名包含模板名与 id（做最小字符清理即可）。

### 2.3 验收
- 导出文件可被再次导入并保持步骤一致。

## 3. 步骤失败事件（P0）

### 3.1 事件要求
- 当某个 step 执行失败时，必须先发出 `STEP_FAILED`，再发出 `RUN_FAILED`。
- `STEP_FAILED.payload` 必须包含：
  - `stepId: string`
  - `stepType: string`（可选，但建议）
  - `error: { code: string; message: string }`

### 3.2 运行记录要求
- run 表应记录最终 `FAILED` 与 `error` 字段。

### 3.3 验收
- 通过构造一个必失败的 selector 用例，能稳定收到 `STEP_FAILED` 与 `RUN_FAILED`。

## 4. WS 心跳与收包处理（P0）

### 4.1 服务端行为
- 必须持续消费客户端发来的消息，避免积压导致断线。
- 对文本消息 `{"type":"PING"}` 可选择：
  - 忽略；或
  - 回复 `{"type":"PONG"}`。

### 4.2 客户端行为
- 继续按既有心跳机制发送 PING。

### 4.3 验收
- 运行过程中保持连接 2 分钟以上不因心跳消息导致断线。

## 5. 测试要求（P1）

- 后端：新增 WS 失败路径脚本（至少验证 `STEP_FAILED`）。
- 前端：E2E 覆盖“导入/导出”至少一条主链路（允许使用固定模板文件）。

总结：0.0.3 的关键是把“能跑”升级为“可交换、可定位、可稳定运行”。
